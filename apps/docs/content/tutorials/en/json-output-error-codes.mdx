One's own results support `-o json` and default to JSON when stdout is not a TTY. Help and passthrough commands such as `one mise` and `one hk` keep their own formats; `one exec` also preserves child output. Distinguish command results from child logs before parsing them.

## 1. The output schema is auto

```bash
# Human-readable in a terminal:
one templates list

# JSON when piped (or with explicit -o json):
one templates list -o json | jq
one templates list | tee templates.json   # piped → JSON
```

The auto-detection is based on whether stdout is a TTY. Explicit:

```bash
one templates list -o json       # force JSON
one templates list -o yaml       # force YAML
one templates list -o text       # force human-readable
```

## 2. Successful output

Output varies by command. This is an excerpt from `one templates -o json`:

```json
{
  "schema": "one-cli/templates/v1",
  "templates": [
    {
      "id": "nestjs-api",
      "name": "NestJS API",
      "toolchain": "node",
      "category": "backend"
    }
  ]
}
```

`schema` identifies a result type; it is not a page URL. Parse the fields for the command you called:

| Command | Result fields |
| --- | --- |
| `one templates` | `schema`, `total`, `templates[]` |
| `one add` | `schema`, `subproject_name`, `target_path`, `template_id`, `toolchain` |
| `one whoami` | `loggedIn`, `expired`, and account details when available; no `schema` or `profiles` |
| `one run <task>` | `schema`, `status`, `exit_code`, `entries`, `tasks` |

Do not assume a shared success envelope. Template names and descriptions follow the CLI language; scripts should use stable IDs.

## 3. The error envelope

One's own structured errors are written to stderr with this envelope. Child failures may instead return their original logs and exit codes:

```json
{
  "schema": "one-cli/error/v1",
  "error": {
    "code": "TEMPLATE_NOT_FOUND",
    "message": "Template 'nestjs-api-typescript' not found.",
    "context": {
      "requested_template": "nestjs-api-typescript",
      "available_templates": ["nestjs-api", "go-api", "nextjs-app", "..."]
    }
  }
}
```

Three rules:

1. **Dispatch on `error.code`**, never on `error.message`. The message is human-readable and changes with the user's `locale` (zh-CN vs en-US).
2. **Read `error.context`** for structured details. Available fields depend on the failure site; see [error codes](/en/docs/error-codes/) for their meaning.
3. **Check the exit code and output source first**. Success results usually go to stdout, while One errors go to stderr. In JSON mode, `one run` sends child logs to stderr, where they may mix with error output. `one exec` preserves child output.

## 4. The dispatch pattern in shell

Save stdout and stderr separately and preserve logs. Dispatch on an error code only when stderr is a valid error envelope; otherwise show the original error.

```bash
error_file=$(mktemp)
trap 'rm -f "$error_file"' EXIT

if output=$(one add nestjs-api --name api -o json --yes 2>"$error_file"); then
  printf '%s\n' "$output" | jq '.subproject_name'
  cat "$error_file" >&2
else
  exit_code=$?
  if code=$(jq -er '.error.code' "$error_file" 2>/dev/null); then
    case "$code" in
      TARGET_EXISTS) printf '%s\n' "Project directory already exists. Choose another name." >&2 ;;
      NOT_ONE_PROJECT) printf '%s\n' "Enter an existing workspace or create one first." >&2 ;;
      *) printf '%s: %s\n' "Unhandled error" "$code" >&2 ;;
    esac
  fi
  cat "$error_file" >&2
  exit "$exit_code"
fi
```

When parsing results:

- i18n changes to the message text
- Future codes added without breaking your script (the `*` arm catches them)
- Check the supported result type for each command where `schema` is provided

## 5. The same pattern for an agent


> Pass `-o json` when reading One structured results. Read `error.code` from error envelopes. Never parse `error.message` — it changes with the user's locale.

In practice, an agent doing "add a NestJS API called user-api" will:

1. Run `one add nestjs-api --name user-api -o json --yes`.
2. If exit code is 0, parse the success envelope and confirm.
3. If `error.code == "TARGET_EXISTS"`, try `user-api-2` or ask the user.
4. If `error.code == "NOT_ONE_PROJECT"`, run `one create` first or ask the user.

Agents can use these recovery patterns directly from command output.

## 6. Key error code groups

Handle errors relevant to your operation and preserve the original cause for other failures. Common groups:

| Group | Examples | Typical handler |
|---|---|---|
| Workspace state | `NOT_ONE_PROJECT`, `WORKSPACE_NESTED_FORBIDDEN`, `MANIFEST_MISSING_OR_EMPTY` | "Run from the workspace root" or "Run `one create` first" |
| Templates | `TEMPLATE_NOT_FOUND`, `TEMPLATE_REQUIRED`, `INVALID_NAME` | List available templates from `error.context` |
| Tools and tasks | `MISE_INSTALL_FAILED`, `MISE_CONFIG_CONFLICT`, `RUNTIME_TASK_NOT_FOUND` | Inspect download or configuration errors; list tasks with `one run` |
| Infisical | `INFISICAL_NOT_CONFIGURED`, `INFISICAL_AUTH_MISSING`, `INFISICAL_AUTH_FAILED` | Sign in and save the first variable to bind storage; sign in again for an expired session |
| Variables | `ENV_UNKNOWN_ENVIRONMENT`, `ENV_SET_OVERWRITE_REQUIRED` | Select a declared environment, or confirm an overwrite with `--yes` |
| Serve | `SERVE_PORT_BUSY`, `SERVE_BIND_FORBIDDEN` | Change the host or port flag, then restart |

Current codes and recovery guidance: [error codes reference](/en/docs/error-codes/).

## 7. JSON output as a CI contract

Use explicit `-o json` in CI and pin the CLI release with `ONE_VERSION`. Replace the example version with your team's chosen release:

```yaml
- run: curl -fsSL https://1cli.dev/install.sh | ONE_VERSION=v0.1.0 bash
- run: one -o json add nestjs-api --name api --yes
```

## Common gotchas

| Symptom | Cause | Fix |
|---|---|---|
| Got a human-readable table instead of JSON in CI | Stdout is a TTY (rare but possible in CI runners) | Pass `-o json` explicitly |
| `jq` cannot parse output | Logs and structured output were combined, or the command passes through raw output | Save stdout and stderr separately; preserve raw logs when parsing fails |
| Different `error.message` across machines | User locales differ | That's expected; dispatch on `code` |
| `schema` field missing | Not every command includes it | Parse the documented command fields; whoami uses `loggedIn` |
