# One NestJS

Read the target project's package.json, src/app.module.ts, src/main.ts, README,
and One manifest before changing the service. Use the user's project name under
services/, discover tasks with `one run`, and run project tasks through One.
The actual project and user choices take precedence over template defaults.

The starter has application information, a database-independent liveness check,
and Swagger documentation. NestJS, class-validator/class-transformer, Drizzle
ORM/Kit, Pino, and Jest remain part of its stack. It has no JWT, login, user CRUD,
database driver, connection, schema, seed, or automatic migration. Add business
features when requested; upstream examples do not make them prerequisites.

Keep the composition in AppModule and bootstrap in main.ts. Create a feature
module when a domain warrants it, with DTOs and providers colocated with its
behavior. Do not add empty controller/service/repository layers for a small
route. Reuse the global ValidationPipe and ordinary Nest HTTP exceptions rather
than introducing another business-code response envelope or token interceptor.

Read runtime configuration from One-injected process environment through the
existing ConfigModule. Preserve ignoreEnvFile; .env.example documents keys but
is not another loading mechanism. Validate new required values when the related
feature is enabled. Keep liveness available without persistence and distinguish
it from readiness if a requested feature needs dependency checks.

When persistence is requested, follow the user's selected database and install
its Drizzle-compatible driver. Add schema, connection ownership, shutdown cleanup,
and Drizzle Kit configuration for that database. Run migration/seed work as
explicit tasks, separate from HTTP startup. Do not default to PostgreSQL, SQLite,
or PGlite, or add a fallback database on connection failure.

Keep Pino's existing basic logging and the OpenAPI document accurate for actual
routes and DTOs. Do not add log rotation, authentication schemes, or response
wrappers unless the requested behavior needs them. One CLI credentials are
separate from application authentication; business skills are installed manually.

Verify typecheck, build, and relevant Jest tests through the project's One tasks.
Use HTTP tests for changed route behavior, including validation and status codes.
The starter's health test must still pass without application auth or database
settings; extend it only when the feature changes that contract.
