# One Expo

Read package.json, app.json, src/app/_layout.tsx, the One manifest, and the project
README. The mobile app lives under apps/<project>. Discover its tasks with
`one run` and use One for development, checks, and builds. Follow the installed
Expo SDK and user choices rather than version assumptions in upstream examples.

The starter uses React Native styles, Expo Router, Axios, SWR, Zustand, MMKV,
Nitro native modules, and an Expo development client. Its home, not-found screen,
and theme switching are the starting surface. Do not introduce NativeWind or
Tailwind, auth/token storage, user screens, or a new remote-data stack as default
infrastructure. Business features and their skills require the user's request.

Keep route entries in src/app/ and reusable components/hooks outside the route
tree. Extend the existing Stack only when navigation needs another screen;
add tabs or animation/gesture dependencies when the feature warrants them.
Preserve safe-area handling, status bar appearance, and the system theme default.
Respect light/dark/system preferences without forcing the device's appearance.

Axios is a thin client using the public EXPO_PUBLIC_API_URL. Public Expo
variables are bundled into the app and must not contain secrets. Let One inject
build/runtime variables; .env.example describes keys rather than adding a second
configuration loader. Do not copy token refresh or business-code interceptors
from an upstream data-fetching example.

SWR owns remote data and caching; use its scoped Map provider to initialize
native focus/reconnect hooks. Keep initFocus and initReconnect cleanup functions.
Online/visibility reads must be synchronous and must not register listeners.
Maintain online state through the existing NetInfo listener, and revalidate on
an offline-to-online or background-to-active transition. Do not add a second
persisted remote cache or listeners inside every isOnline call. Web should use
SWR's normal browser event handling rather than native lifecycle hooks.

Zustand owns shared UI preferences; local component state stays in React and
remote data stays in SWR. Persist preferences through the existing MMKV adapter.
MMKV/Nitro need a native development client; Expo Go cannot validate them. Keep
native and web behavior compatible, and avoid native-only side effects during
web prerendering. Do not add AsyncStorage or SecureStore merely to duplicate the
existing UI preference storage.

Check SDK dependency compatibility with the installed Expo CLI's `install --check`
through a project task. Verify relevant typechecks, tests, and web export; use a
native development build for native changes. Listener tests should cover state
transitions and cleanup. State clearly which platforms/devices were exercised;
a passing web export does not prove iOS/Android runtime compatibility.
